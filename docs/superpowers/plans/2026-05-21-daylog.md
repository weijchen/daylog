# daylog Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build `daylog`, a vault-less, dependency-free Claude Code plugin providing a deliberate daily plan → check → reflect loop, packaged for open-source release.

**Architecture:** Pure-prompt Claude Code plugin — no executable code. Four Markdown slash-command definitions (`init`/`start`/`check`/`end`), a daily-file template, a fixed-path Markdown config, plus packaging (plugin/marketplace manifests, README, license, example, contribution docs). Commands instruct Claude to read config, gather context (git via Bash + optional hooks), and read/write one Markdown file per day.

**Tech Stack:** Claude Code plugin format (Markdown commands + `.claude-plugin/*.json`), Bash/git for context gathering, Python 3 (stdlib only) for JSON validation during testing.

---

## Verification approach (read first)

This is a **prompt-only** plugin, so there is no compiled code and no unit-test framework. Verification has two forms, both used below:

1. **Static checks** — exact shell commands (JSON validity, file existence, required-section/placeholder grep). Deterministic; run as written.
2. **Behavioral checks** — install the plugin locally and run the slash command in a Claude Code session against a **scratch config** so real data is untouched. Each behavioral task specifies the exact setup, the command to run, and the resulting file state to grep for.

**Scratch environment** used by behavioral tasks (set up once, in Task 4):
- Scratch config path is the real fixed path `~/.config/daylog/config.md`. To avoid clobbering a real one, back it up first: `cp ~/.config/daylog/config.md ~/.config/daylog/config.md.bak 2>/dev/null || true`, and restore at the end.
- Scratch storage root: `/tmp/daylog-test/`
- Scratch repo set: `/tmp/daylog-dev/` containing two git repos with commits dated "today".

**Local install for behavioral tests:**
```bash
mkdir -p ~/.claude/plugins/local
ln -sfn "$(pwd)" ~/.claude/plugins/local/daylog
```
Then in a Claude Code session: `/plugin` → enable the local `daylog` plugin (or it is auto-discovered from `~/.claude/plugins/local`). Commands appear as `/daylog-init`, `/daylog-start`, etc.

## Task 5: `/daylog-start` command

**Files:**
- Create: `commands/daylog-start.md`

- [ ] **Step 1: Write the command**

````markdown
---
description: Morning planning — create today's day file with your focus
argument-hint: ""
allowed-tools: [Read, Write, Edit, Glob, Grep, Bash, AskUserQuestion]
---

# /daylog-start — Morning Plan

## Constants
- **Config path**: `~/.config/daylog/config.md`
- **Today**: current system date, format `YYYY-MM-DD`

## Process

### 1. Read config
Read `~/.config/daylog/config.md`. Extract `storage_root`, `language`, `repos`. If the config is missing, tell the user to run `/daylog-init` first and stop.

### 2. Gather context (in parallel)
- **Yesterday's summary**: list `{storage_root}/*.md`, pick the most recent file whose date is before today, and read its `## Summary` section. (There may be gaps — use the latest prior file, not strictly yesterday.)
- **Git state**: resolve `repos`:
  - If `repos` is `scan {DIR} one level deep`: run `for d in {DIR}/*/; do [ -d "$d.git" ] && echo "$d"; done`.
  - Otherwise treat `repos` as explicit paths.
  For each repo, collect current branch (`git -C {repo} rev-parse --abbrev-ref HEAD`), today's commits (`git -C {repo} log --oneline --since="$(date +%F)T00:00:00"`), and uncommitted changes (`git -C {repo} status -s`).
- **Hooks**: for each hook in config, run its command and capture stdout.

### 3. Present a concise context summary
Show: carryover from the latest prior summary, current git state, and any hook output. Keep it brief.

### 4. Ask the user (AskUserQuestion)
1. "What's your focus today?" — free text (the day's priorities)
2. "Anything to defer or drop?" — free text (optional)

### 5. Create today's day file
Copy the plugin's `templates/day.md` and fill tokens:
- `{{DATE}}` → today
- `{{FOCUS}}` → the user's focus
- `{{CARRYOVER}}` → unfinished items from the latest prior summary + the user's defer/drop notes
- `{{CONTEXT}}` → the git state and hook output gathered in step 2

Write to `{storage_root}/{today}.md`. If the file already exists, ask whether to overwrite or open the existing one.

Generate all text in the configured `language`.

### 6. Validate & show
Read the file back, confirm the frontmatter `date` matches today and the three plan sections are populated. Display for approval; edit on request.
````

````markdown
---
description: End of day — auto-summarize the day, then reflect and record
argument-hint: ""
allowed-tools: [Read, Write, Edit, Glob, Grep, Bash, AskUserQuestion]
---

# /daylog-end — Wrap-up

## Constants
- **Config path**: `~/.config/daylog/config.md`
- **Today**: current system date, format `YYYY-MM-DD`

## Process

### 1. Read config, today's file, and the day's signals
Read `~/.config/daylog/config.md` for `storage_root`, `language`, `repos`.
Read `{storage_root}/{today}.md` for the morning `Focus` and the `Progress` checkpoints.
Gather **today's git commits** across the resolved `repos` (`git -C {repo} log --oneline --since="$(date +%F)T00:00:00"`).
If today's file does not exist, warn the user and offer to create a minimal one or stop.

### 2. Summarize step (auto-draft)
Synthesize the morning `Focus`, the `Progress` checkpoints, and today's git commits into a draft 2–4 sentence `## Summary` of the day. Present this draft to the user.

### 3. Confirm and reflect (AskUserQuestion)
1. "Here's the draft summary — adjust anything?" — user edits/approves the summary.
2. "What did you learn today? (optional)" — learnings.

### 4. Write the record
Fill the day file's previously-empty sections (do not touch `Focus`/`Carryover`/`Context`/`Progress`):
- `## Summary` → the confirmed summary. (This is what tomorrow's `/daylog-start` reads as "yesterday".)
- `## Done / Carryover` → completed items (cross-referenced with the morning Focus) and what rolls to tomorrow.
- `## Learnings` → the user's learnings, if any.

Write in the configured `language`.

### 5. Validate & show
Read back; confirm `Summary` is non-empty. Display the completed file for approval; edit on request.
````

## Task 8: README

**Files:**
- Create: `README.md` (overwrite the placeholder)

- [ ] **Step 1: Write the README**

Write `README.md` with these sections (real content, not headings-only):

```markdown
# daylog

A deliberate daily **plan → check → reflect** loop for developers — as a Claude Code plugin. Vault-less, dependency-free, plain Markdown.

`daylog` is a *human-facing* journal and planner. It is **not** an automatic agent-memory tool: nothing is captured in the background and nothing is injected into your sessions unless you ask. You decide, in your own words, what each day means and what carries forward. (If you want automatic session memory, see the official Remember plugin instead — daylog is the deliberate, human-authored counterpart.)

## The daily loop

| Command | When | What it does |
|---|---|---|
| `/daylog-init`  | once    | Creates your config (`~/.config/daylog/config.md`) and storage directory. |
| `/daylog-start` | morning | Pulls yesterday's summary + today's git state, asks your focus, writes today's plan. |
| `/daylog-check` | midday  | Loads today's context into the session and logs a timestamped progress note. |
| `/daylog-end`   | evening | Auto-drafts a summary from git + your checkpoints, you refine it, then records the day. |

Each day is one file: `YYYY-MM-DD.md`. The evening summary is what next morning reads as "yesterday" — that's the loop.

## Install

```
/plugin marketplace add USERNAME/daylog
/plugin install daylog
```
Then run `/daylog-init`.

## Configuration

`~/.config/daylog/config.md`:

- `storage_root` — where day files live (default `~/daylog`)
- `language` — output language (default `en`)
- `repos` — `scan ~/Dev one level deep`, or explicit paths
- `hooks` — optional shell commands whose output is added as context (e.g. a Linear/GitHub CLI)

## Context sources

- **Git (built-in):** today's commits, current branch, uncommitted changes across your configured repos.
- **Hooks (optional, opt-in):** any shell command — that's how external services plug in without daylog depending on them.

## Customizing & localizing

Day-file structure and section headings live in `templates/day.md`. Edit it to change the layout or translate the headings. Output text language is set by `language` in config.

## License

MIT.
```
